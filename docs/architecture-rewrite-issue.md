## Deep Module Architecture Rewrite

Refactor the codebase from shallow layered architecture (5 layers, ~80 pass-through functions) to deep domain modules with small interfaces hiding large implementations. Based on John Ousterhout's "A Philosophy of Software Design" — a deep module's value = functionality / interface complexity.

**Current problem:** Any operation crosses 5 layers (UI → Context → Tauri Wrapper → Rust Command → DB). Most layers are shallow pass-throughs that add interface complexity without adding logic. Types drift between Rust and TypeScript. State machines are duplicated across languages.

**Solution:** 7 sequential commits collapsing these layers into domain modules. Each module owns its types, IPC, state, and logic behind a small interface (2-6 methods).

### Architecture Decisions

| Decision                            | Choice                                                      | Rationale                                                                  |
| ----------------------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------- |
| ts-rs adoption                      | Foundation-first (Commit 1)                                 | Clean cut — all types generated before module work begins                  |
| PR strategy                         | One PR, 7 sequential commits                                | Each commit = one architectural change, app stays functional               |
| Migration strategy                  | Delete-and-replace (frontend), wrap-and-inline (DB layer)   | Few consumers on frontend (compiler catches breaks); many consumers for DB |
| Module location                     | `src/lib/modules/<name>/`                                   | Preserves `$lib` alias, co-locates tests, allows internal helpers          |
| GitHub + Git Status merge           | Merge in Rust, single `VersionControlState`                 | Eliminates type drift, `ready-to-merge` bug, and string vs enum mismatch   |
| Module name for GitHub + Git Status | `version-control`                                           | Descriptive over abbreviation                                              |
| Database concurrency                | `r2d2-sqlite` connection pool                               | Battle-tested, enables concurrent readers with WAL mode                    |
| Shared types                        | ts-rs-generated types; modules import from generated output | Single source of truth in Rust                                             |

### Module Structure (Final State)

```
src/lib/
  modules/
    sessions/
      index.svelte.ts          # Deep module: context + IPC + types + state machine
    version-control/
      index.svelte.ts          # Deep module: GitHub + Git Status merged
    issues/
      index.svelte.ts          # Deep module: CRUD + label serialization
    visualization/
      index.ts                 # Deep module: pure functions, no Svelte reactivity
    board/
      index.svelte.ts          # Deep module: dashboard + palettes + preferences
    notifications/
      index.svelte.ts          # Deep module: notification routing + config
    actions/
      index.svelte.ts          # Deep module: action templates + execution
  types/
    generated/                 # ts-rs output — DO NOT EDIT manually
      index.ts                 # Barrel re-export of all generated types
    shared.ts                  # Cross-module contracts not generated by ts-rs (if any)
  reactivity/                  # Kept — shared primitives used by modules
    state.svelte.ts
    persisted.svelte.ts
  components/                  # Kept — UI components import from modules
```

**Deleted after all commits:**

- `src/lib/context/` — absorbed into modules
- `src/lib/tauri/` — absorbed into modules (IPC is implementation detail)
- `src/lib/types/*.ts` — replaced by ts-rs generated types + module-internal types
- `src/lib/engine/` — absorbed into visualization module

## Commit 2: Database Layer — r2d2-sqlite Connection Pool

### Goal

Replace the single `Mutex<Connection>` with an `r2d2` connection pool for reads + a dedicated write connection. SQLite WAL mode already supports concurrent readers; this commit unlocks that capability.

### Context for Subagent

This is commit 2 of 7. Commit 1 (ts-rs) is already done. You are ONLY changing the Rust database layer — no frontend changes. Every Rust command file that accesses the database needs to change how it acquires a connection. The session actor (`session_actor.rs`) has its own `open_actor_connection()` — leave that as-is (it's already independent).

This commit uses the **wrap-and-inline** migration strategy: change `DatabaseState` first, then update all consumers. If a command does any writes, it uses the write connection. Read-only commands use the pool.

### What to Do

**1. Add dependencies to `src-tauri/Cargo.toml`:**

```toml
r2d2 = "0.8"
r2d2_sqlite = "0.24"   # Must match rusqlite 0.31
```

Verify `r2d2_sqlite` version compatibility with `rusqlite = "0.31"`.

**2. Rewrite `src-tauri/src/database/connection.rs`:**

Current (39 lines):

```rust
pub struct DatabaseState(pub Mutex<Connection>);
```

New:

```rust
use r2d2::Pool;
use r2d2_sqlite::SqliteConnectionManager;

pub struct DatabaseState {
    pub read_pool: Pool<SqliteConnectionManager>,
    pub write_conn: Mutex<Connection>,
}
```

The `initialize_database` function should:

- Create a `SqliteConnectionManager` pointing to the same DB file
- Build a pool with `max_size: 4` (4 concurrent reader connections)
- Each reader connection gets `PRAGMA journal_mode=WAL; PRAGMA foreign_keys=ON;`
- The write connection is the existing single connection (just like today)
- Return `DatabaseState { read_pool, write_conn }`

**3. Add helper methods to `DatabaseState`:**

```rust
impl DatabaseState {
    pub fn read(&self) -> r2d2::PooledConnection<SqliteConnectionManager> {
        self.read_pool.get().expect("Failed to get read connection from pool")
    }

    pub fn write(&self) -> std::sync::MutexGuard<'_, Connection> {
        self.write_conn.lock().expect("Failed to lock write connection")
    }
}
```

**4. Update all command files:**

Pattern for read-only commands (any command that only does SELECT):

```rust
// Before:
let db = state.0.lock().unwrap();
let mut stmt = db.prepare("SELECT ...")?;

// After:
let db = state.read();
let mut stmt = db.prepare("SELECT ...")?;
```

Pattern for write commands (INSERT, UPDATE, DELETE):

```rust
// Before:
let db = state.0.lock().unwrap();
db.execute("INSERT ...", params![...])?;

// After:
let db = state.write();
db.execute("INSERT ...", params![...])?;
```

Pattern for mixed commands (read then write, like `sync_all_github_state`):

```rust
// Read phase — use pool
let issue_ids = {
    let db = state.read();
    // ... SELECT query
};
// Write phase — use write conn
let db = state.write();
// ... INSERT/UPDATE queries
```

**Command files to update (all in `src-tauri/src/commands/`):**

- `issue_commands.rs` — mixed (CRUD)
- `session_commands.rs` — mixed (read sessions + update state)
- `github_commands.rs` — mixed (`sync_all_github_state` reads then writes)
- `git_status_commands.rs` — mixed (`refresh_git_status` writes cache)
- `worktree_commands.rs` — mixed
- `action_commands.rs` — mixed
- `color_palette_commands.rs` — mixed
- `notification_commands.rs` — mixed
- `portfolio_commands.rs` — mixed
- `label_shape_mapping_commands.rs` — mixed
- Also: `database/schema.rs` if it accesses the connection for migrations

**5. Update `src-tauri/src/lib.rs`:**
The `.manage(database_state)` call stays the same — `DatabaseState` is still managed state. The type just has different internals.

**6. Leave `open_actor_connection()` unchanged:**

## Cross-Cutting Concerns

### Import Convention

After all commits, the import pattern is:

```typescript
// Generated types (from Rust via ts-rs)
import type { Issue, Session, Dashboard } from '$lib/types/generated';

// Module APIs
import { useIssues } from '$lib/modules/issues';
import { useSessions } from '$lib/modules/sessions';
import { useVersionControl } from '$lib/modules/version-control';
import { useBoard } from '$lib/modules/board';
import { useNotifications } from '$lib/modules/notifications';
import { useActions } from '$lib/modules/actions';

// Pure functions
import { computeVisualization, computeForestLayout } from '$lib/modules/visualization';

// Reactivity primitives (shared)
import { Persisted } from '$lib/reactivity/persisted.svelte';
```

### Testing Strategy

- **Replace, don't layer:** Old context tests (if any existed) are replaced by module boundary tests
- **Engine tests migrate:** `compute_tree_visualization.test.ts` and friends move into their module
- **New tests:** Each module should have at least smoke tests for its public interface
- **Rust tests:** Existing inline tests stay. Add tests for new commands (`get_version_control_state`, etc.)

### Reactivity Primitives

The `src/lib/reactivity/` directory stays shared. Modules should prefer `StateRaw<T>`, `ReadonlyState<T>`, `ProtectedState<T>`, and `Persisted<T>` over raw `$state` where they add value (equality checks, read-only guarantees, localStorage persistence). This was an existing codebase convention that was underused.

### Naming Convention

- Module folders: kebab-case (`version-control`, not `versionControl`)
- Module entry point: always `index.svelte.ts` (or `index.ts` for pure modules)
- Context hooks: `use<ModuleName>()` (e.g., `useVersionControl()`)
- Context setup: `set<ModuleName>Context()` (e.g., `setVersionControlContext()`)
